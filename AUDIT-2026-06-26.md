# Discordmaxxer Resilience + QoL Audit — 2026-06-26

Multi-agent audit: 8 dimensions, 60 findings, adversarially verified (58 kept, 2 refuted).
Target: works as flawlessly as possible with best QoL for normal users AND competitive gamers (low input delay).

## 1. One-line verdict
Core voice/echo/zstd plumbing is genuinely solid, but the resilience layer (no periodic update check + auto-publish-stable-on-build-only) and one advertised TournamentMode benefit (30fps cap) are the real liabilities — nothing is crashing today, but a bad auto-shipped build could reach everyone with no recovery path, and several "it's protected/throttled" claims don't match the architecture.

## 2. CRITICAL / HIGH issues (verifier downgraded all to medium — real but bounded)

**H1 — Auto-rebump can auto-publish a STABLE release to all users gated only on build success, not runtime voice.** [CONFIRMED]
- `.github/workflows/vencord-shc-autobump.yml:92-119` runs `electron-builder --publish always` if rebrand-warnings=0 and `pnpm build` passes. Build-clean != voice-works — the 2026-06 zstd/DAVE outage built perfectly and broke voice for everyone. Combined with `updater.ts:53` autoInstallOnAppQuit=true.
- Fix: emit a **prerelease** tag so only DMBeta opt-in users canary it (`allowPrerelease` infra already exists), promote to stable manually after a live call passes.

**H2 — No periodic update check; long-running clients never discover a fix until restart.** [CONFIRMED]
- `src/main/updater.ts:61-62` calls `checkForUpdates()` exactly once at startup; no `setInterval`. CLAUDE.md's "polls ~12h" claim is false.
- Fix: `setInterval(() => autoUpdater.checkForUpdates().catch(()=>{}), 6*60*60*1000)`, paused while a download/install is in flight.

**H3 — TournamentMode 30fps renderer cap is a silent no-op that falsely self-reports success.** [CONFIRMED]
- `discordmaxxerPerf.ts` `wc.setFrameRate(30)` only acts under offscreen rendering (this app is windowed) — silently returns, but `frameRateLimited=true` is still reported and the toast shows "fps→30". Zero GPU work saved. (Priority drop + arRPC teardown DO work.)
- Fix (min): stop claiming fps→30. Fix (real lever): when TM active + Discord occluded behind a fullscreen game, conditionally re-enable `backgroundThrottling` (force-disabled at `index.ts:73-75`, `mainWindow.ts:337`) so Chromium throttles the hidden window to ~1fps. Needs live voice test.

**H4 — No global push-to-talk / mute / deafen keybind — the #1 competitive voice control is missing.** [CONFIRMED]
- OS-level hotkey bridge exists (`discordmaxxerHotkeys.ts:37-55`) but only TM + CompactView use it. DMStreamMute's Ctrl+Shift+M is window-focused → useless in a fullscreen game.
- Fix: DMVoiceKeybinds plugin → global toggle-mute + toggle-deafen via the existing bridge → FluxDispatcher. (True hold-to-talk infeasible: globalShortcut has no keyup.) Infra exists — low effort, highest competitive leverage.

**H5 — hardwareVideoAcceleration defaults OFF → screenshare send may be locked to software encoder.** [UNCERTAIN]
- `index.ts:55` gates `AcceleratedVideoEncoder` behind the flag; defaults false. Maintainer comment says WebRTC desktop-capture is software "regardless of the toggle" — but that comment cites stale m134; Electron 41 = Chromium 146. Warrants a live retest.
- Fix: do NOT blindly default-on (warning: graphical glitches / infinite-loading streams). Live-verify outbound encoder stats with flag ON on m146 (human-only). Cheap half = wire the existing software-encoder health toast to a one-tap "Enable HW encoding & restart" button + auto-revert.

## 3. TournamentMode-vs-audio (direct answer)
**Just-applied audio/network-exclusion fix: CORRECT. Sufficient: NO.**
- Correct (keep): `PROTECTED_UTILITY_RE` spares Audio Service (device I/O) + Network Service (RTC transport) from BELOW_NORMAL. Electron reports those exact names.
- Residual risk: the **renderer** still drops to BELOW_NORMAL, and Opus encode/decode + NetEq jitter buffer run on WebRTC threads INSIDE the renderer — so a CPU-pegged single-PC streamer can still stutter. (GPU process drop also starves an active HW screenshare encode.)
- Bounded: Windows runs those WebRTC realtime threads at TIME_CRITICAL/MMCSS regardless of process class.
- Next step: gate the renderer (and GPU) drop on a `voiceActive`/`streamActive` flag from `VOICE_CHANNEL_SELECT` — keep GPU/main savings otherwise. Then live-verify under a fully CPU-pegged game via the Stream & Voice Health panel.

Competitive:

2. One-tap "Enable HW encoding & restart" from the software-encoder toast (H5).
3. Keep renderer/GPU at NORMAL while in voice/streaming under TM (§3).

Normal QoL:
4. Reconsider surprising default-on plugins — SilentTyping (friends never see you typing) + NewGuildSettings (auto-mutes every joined server → missed @mentions) → opt-in or surface in onboarding. [medium]
5. MessageLogger default-on stores others' deleted DMs unbounded on disk → off-by-default or retention cap + explainer. [medium]
6. Persist arRPC restore intent to disk — crash/quit with TM on leaves Rich Presence silently disabled forever (in-memory `priorArRpc` lost). [medium]
7. Echo-fix quiet-start gap — Go-Live during a loading screen trips the 3s `waitForSignal` → echoing loopback for the whole session. Distinguish "dead capture" (0 IPC chunks) from "momentarily silent" (chunks below peak). [medium]
8. Consolidate 3 stacked first-run consent walls into one DMWelcome surface. [low]

## 5. Already solid — do NOT touch
- zstd/DAVE voice fix (`index.ts:136-137`) — documented, backstopped by DMVoiceGuard.
- winaudio exclude-self echo path — defensively staged (float check, live-track check, 3s confirm-before-cut, AudioContext.resume, correct IAgileObject QI, PID in main). Robust aside from quiet-start gap (#7).
- audio/network utility-process exclusion (§3 correct part).
- TM design: BELOW_NORMAL over IDLE, real arRPC worker teardown, renderer-reload recovery via `set(false)` + `on===state.on` guard.
- contentHint='motion' default — spec-correct for gameplay, keeps HW-encoder eligible.
- Adaptive bitrate (0.15 bpp up to 8 Mbps) — sound; scope any marketing claim to Nitro tiers (server caps non-Nitro ~2.5 Mbps/720p30).

Honesty fixes to batch: temper TM "input latency reduction" → "frees CPU on constrained systems" (priority drop is near-placebo on idle 6+ core rigs); add CrashHandler explicitly to `PLUGINS_DEFAULT_ON`.
